## 权限与同伴代码衔接

- 后端始终调用既有 `IsbfLearning.can_manage?(guardian)`，前端使用原有 `academy_moderator_permissions.manage_resources`。原生 admin 保持完整权限；普通版主不会因身份自动得到权限。审核继续使用 `can_review?`。
- 用户提供的同伴会话记载 `PUT /courses/:id`、`Courses.update(user, id, name:, grade:)`、稳定课程 ID、归档目录及数据库行锁。本次保持同名接口和方法签名，更新目录时保留 `deleted_at` 等归档信息，并复用 `with_catalog_lock`。后续合并同伴的科目删除实现时，保留其删除、回收站和审核事务保护；不要重复注册更新路由、定义第二套更新方法或新建目录存储。
- 同伴旧方案的 `ensure_admin!` 会拒绝具有资源管理权限的学院管理员，与本次用户的新要求冲突。合并时该调用需统一改为现有 `can_manage?`，不能恢复单独的原生 admin 限制。沿用已有课程管理菜单时，将本次编辑动作接入该菜单，移除重复的独立编辑按钮，保持一个入口。
- 本次不新增课程删除，也不对正式数据执行删除。现有资料删除仍使用二次确认及原生软删除，删除验证仅使用隔离环境的合成资料。

## 贡献归属与数据

资料真实作者保持不变。可选学号通过已安装学院插件的已注册身份精确查找，管理员必须主动选择对应用户；仅存姓名不会关联其他账号。关联保存为 Topic custom fields。学号与关联用户 ID 只向获管理权限的账号序列化，普通列表不公开学号。

“我的贡献”只查询当前会话账号的有效已发布资源；显式关联优先于上传者，历史无关联资源按真实上传账号归属。查询不接受客户端指定其他用户。待审核、拒绝、隐藏、已删除、失效课程及无分类访问权限的资料不显示。重新关联、修改及删除后重新请求列表，避免保留旧结果。
